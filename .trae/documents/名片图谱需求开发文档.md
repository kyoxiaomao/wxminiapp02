# 名片图谱 需求开发文档

> 版本：v0.1（需求探讨稿）｜日期：2026-10-06
> 状态：待评审（含 4 个开放决策，见 §8）

---

## 1. 产品定位

一句话：**以图谱可视化管理人脉的微信小程序**——每个人是一张名片，每段关系是一条带标签的边，照片按人归档。

四 Tab 结构：**图谱 ｜ 名片 ｜ 相册 ｜ 我的**

核心价值主张：把“躺在微信通讯录和手机相册里的一团乱麻”变成“一眼看清的关系网络”。

---

## 2. 目标用户与核心场景

| 用户 | 核心场景 | 图谱类型 |
|---|---|---|
| 大家族长者/家族成员 | 录入三代亲属，看清辈分与称谓 | 家族 |
| 商务人士/销售 | 按公司管理客户，见客户前回顾关系 | 公司、客户 |
| 兴趣组织者（车友会/钓友群） | 活动中拍的照片按人归档 | 车友、钓友 |

三个必须跑通的主链路：
1. **建图谱**：建家族图谱 → 逐个添加节点（头像+昵称）→ 关联名片 → 标记关系
2. **拍照片**：活动拍照 → 上传时圈选图中的人（取自图谱节点）→ 按人名搜到全部照片
3. **换名片**：生成个人名片 → 分享卡片/二维码给对方 → 对方保存为名片

## 3. 功能架构

### 3.1 图谱 Tab（核心差异化）

- 图谱列表：封面、名称、类型标签（家族/公司/客户/车友/钓友/自定义）、成员数
- 创建图谱：选类型（不同类型预置不同关系标签与布局，见 §6）
- 图谱画布：
  - 节点 = 头像 + 昵称（+角色/称谓），选自名片库或新建匿名节点
  - 边 = 关系标签（家族：夫妻/父子/母子/兄弟姐妹；公司：上下级/同事/合作；自定义）
  - 交互：拖拽、缩放、点击节点弹详情（名片摘要 + 照片入口 + 关系列表）
- 节点操作：添加、编辑昵称、关联/更换名片、删除

### 3.2 名片 Tab

- 名片字段：姓名、电话、公司、职位、头像、照片（可多张）、备注
- 名片列表 + 搜索（姓名/电话/公司）
- 创建方式：手动录入、微信导入（授权头像昵称）、扫名片二维码
- 分享：生成小程序卡片与二维码，转发微信群/好友
- 收到的名片进入名片库

### 3.3 相册 Tab

- 上传照片（拍照/从相册选），上传时圈选图中人物（取自图谱节点，可多选）
- 视图：时间线网格 + 按图谱/人筛选
- **搜索人**：输入人名 → 该人名下所有照片
- 照片详情：时间、涉及的人（可跳名片）、来源图谱

### 3.4 我的 Tab

- 个人信息（头像、昵称，微信授权）
- 我的名片（对外展示的那张）
- 会员中心：权益对比、开通/续费
- 设置：隐私、数据导出、账号

## 4. 核心数据模型（最关键的架构决策）

```
User 用户 ──< Membership 会员
User ──< Card 名片（全局唯一实体：姓名/电话/公司/职位/头像/照片集）
Card 被挂在 Node 上（卡片节点，挂多个）
Node 图谱节点（属于 Graph，昵称/角色，可无名片（匿名节点））
Graph 图谱 ──< Node ──< Edge 关系（source → target，带关系标签）
Photo 照片 ──< 圈选的人（Node 列表）
```

三条实体规则：
1. **名片全局唯一**：同一个人（如“父亲”）在家族图谱和公司图谱中是同一张名片，改一处全局生效。
2. **图谱只存引用**：Node 是 `Graph + Card` 的组合，昵称是图谱内的显示层（“张伟”在家族图谱里显示“三叔”）。
3. **照片挂在 Node 上**：既能按人搜，也能按图谱聚合（家族相册/车友会活动相册）。

## 5. 技术选型建议

| 层 | 选型 | 理由 |
|---|---|---|
| 框架 | Taro 4 + TypeScript | 跨端，未来可出 H5/抖音端 |
| 后端 | 微信云开发（云函数+云数据库）起步 | 免运维，个人开发者可快速上线；用户量上来再迁自有后端 |
| 图谱渲染 | SVG（节点 < 100）或 Canvas（节点多/动画频繁） | 复用现有 index.html demo 的力导向布局视觉（力导向可选） |
| 图谱布局 | 家族=分层树（按辈分），社交类=力导向网络 | 关系类型决定视觉语义，不做单一布局 |
| 图片存储 | 云存储 CDN | 照片上传 + 缩略图 |

## 6. 商业化（会员）

| 权益 | 免费 | 会员 |
|---|---|---|
| 图谱数量 | 2 个 | 无限 |
| 每图谱节点 | 50 | 500 |
| 相册照片数 | 200 张 | 不限 |
| 人脸/按人搜索 | 基础 | 高级分析 |

> 付费点必须挂“容量”（节点/照片），这是与产品价值直接相关的稀缺资源。

---

## 7. MVP 范围与迭代

- **P0（MVP，单机体验，不做云端同步）**：图谱 CRUD + 节点 + 关系标签；名片 CRUD + 搜索；相册上传 + 手动圈人 + 按人搜；我的 + 会员占位页。
- **P1（社交价值）**：名片分享卡片/二维码交换；关系标签预设库；家族树/力导向布局切换。
- **P2（增长）**：图谱多人共建（家庭成员共同维护一个家族图谱——这是天然的裂变场景）；数据导出；多端。

## 8. 开放决策（需产品拍板，影响架构）

1. **名片交换是单方录入还是双方确认？**
   单方录入他人信息存在隐私合规风险（个人信息保护法），建议“分享卡片 → 对方保存”或以“我保存关于他的信息+照片”定性。影响 P1 的交换流程设计。
2. **同一人多图谱共用的是同一张名片，还是每图谱独立？**
   本文档采用“全局唯一名片 + 图谱内昵称显示层”，若产品要“不同圈子看到不同侧面”，则需改为每图谱独立名片实例，数据模型复杂度上升。
3. **照片按人标记：手动圈选 vs 人脸识别？**
   手动圈选成本高但准确、零合规风险；人脸识别体验好但成本高（云调用计费）、敏感个人信息需单独同意。建议 MVP 手动，P2 再评估。
4. **图谱是否支持多人协作共建？**
   共享/共建带来裂变，但引入权限模型和云端同步，工作量翻倍。是否纳入近期规划影响后端架构选型。

---

## 9. 非目标（本期明确不做）

- 不做即时通讯/聊天（图谱不是社交 App，止步于“关系与名片的记录”）
- 不做朋友圈/社区内容流
- 不做 AI 智能推荐人脉（远期可议）
