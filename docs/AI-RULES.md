# 名片图谱 —— AI 必守规则

> 微信小程序：Taro 4 + React 18 + TypeScript + 微信云开发（CloudBase）。界面文案和代码注释用中文。

## 一、工作流程

1. **先写清单，用户同意后再改代码**：`docs/V{版本}开发清单.md`，小改也要有。只改文档不算改代码。
2. 清单分五节：要求和决定（分清「用户定的」和「我定的默认做法，等确认」）、改哪些地方、分几步怎么查、验收清单、实现记录。
3. 需求不清楚先问，不自己定范围。用户问问题时只回答，不接着改。
4. **在功能分支上开发，不直接改 `main`**。分支名用 `v{版本}-{内容}`。
5. 写完跑检查（第三节），补清单的实现记录（这一轮踩的坑、总结的经验也写在这里），推到功能分支，交给验收。

## 二、验收链路（Windows 机子负责）

Windows 机子主要做验收和收尾，顺序不能乱。**每一步出问题就停下，告诉用户，不往下走。**

| 步骤 | 做什么 | 命令或位置 |
|---|---|---|
| 1. 取分支 | 拉到最新的功能分支 | `git fetch`，`git switch <分支>`，`git pull --ff-only` |
| 2. 检查 | 类型检查和构建都要过 | `npm ci --legacy-peer-deps`（没装依赖时），`npx tsc --noEmit`，`npm run build:weapp` |
| 3. 部署云函数 | 分支改了 `cloudfunctions/` 才做，只部署改过的 | 微信开发者工具上传。**项目只有一个云环境，部署就是上线，先告诉用户** |
| 4. 验收 | 按清单的验收清单，开发者工具导入项目根目录（产物在 `dist/`），再真机走一遍；活名片要两个微信号 | 不通过就回功能分支改，从第 1 步重来 |
| 5. 归档 | **用户明确说验收通过后**，补完实现记录，状态改成已验收，清单移到归档，在功能分支提交 | `git mv docs/V{版本}开发清单.md docs/归档/` |
| 6. 合并到 main | main 先更新，再合并 | `git switch main`，`git pull --ff-only`，`git merge --no-ff <分支>` |
| 7. 提交推送 | 合并后的 main 过一遍第 2 步的两项检查，再推送 | `git push origin main` |
| 8. 删分支 | **确认第 7 步推送成功后才删** | `git push origin --delete <分支>`，`git branch -d <分支>` |

- 第 5～8 步要用户说了才做。说「推送」只推当前分支，不等于合并到 main。
- 上传小程序代码、提交微信审核由用户在开发者工具里做。
- 云端的删除操作（删云函数、删集合）恢复不了，每次单独确认。

Windows 机子的两个注意点：

- 本机没配 git 用户名：提交时加 `-c user.name=... -c user.email=...`，沿用上一次提交的作者，不改配置。
- git 卡住时先查 `git config core.sshCommand`（用 Git 自带的 ssh 和本项目的密钥），不要换端口。

## 三、代码检查

```powershell
npx tsc --noEmit          # 必须 0 个错误
npm run build:weapp       # 必须通过
node --check cloudfunctions/<函数名>/index.js   # 改了云函数
```

项目没有自动化测试，界面和云端行为要靠第二节验收，没验过的不说「好了」。

## 四、硬规则

1. **不写兜底**：出错直接抛出或提示用户，不吞错、不用假数据。
2. **删东西要彻底**：连同样式、import、未用变量、过期注释一起删。

## 五、文档

`docs/` 根目录只放正在进行的清单和本文，做完的移到 `docs/归档/`，除非用户要求，不读归档。
