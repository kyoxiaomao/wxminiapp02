## 一、产品定位与 V1.0 目标

**一句话定位**：以「图谱」组织人脉与关系的小程序，一张名片全局唯一，在不同图谱里以不同称谓出现。

V1.0 要完成的最小闭环：

1. 用户微信登录 → 首登建立自己的名片
2. 创建图谱（家族 / 公司 / 客户 / 车友 / 钓友 / 自定义）
3. 在画布上添加人物节点、连线、标注关系
4. 把名片转发给别人，收下后自动成为「活名片」，源卡更新后可感知
5. 名片可在多个图谱间复用，称谓按图谱独立

**不在 V1.0 的核心取舍**：不做多人实时协作、不做名片认领授权闭环、不做 OCR/vcf 导入、不做管理后台。

## 六、已知限制与风险

| # | 问题 | 影响 | 处理建议 |
|---|---|---|---|
| 1 | 图谱分享未实现 | 缺少「图谱→群→新用户」裂变入口 | V1.0 收尾补齐 |
| 2 | 头像/昵称未用微信一键能力 | 首登录入成本高、转化低 | V1.0 收尾补齐 |
| 3 | 无认领授权机制 | 他人可被单方录入，存在《个保法》与审核风险 | V1.1 做 `shares` 闭环，V1.0 仅限本人/演示数据 |
| 4 | 活名片靠打开时比对版本 | 无法实时提示更新 | V1.1 接数据库 `watch` |
| 5 | 手机号依赖企业主体 | 个人主体无法使用 `getPhoneNumber` | 保留手填兜底 |
| 6 | 云函数运行时不一致 | `login/seed` 为 Nodejs16.13，其余为 Nodejs20.19 | 统一到 20.19 |
| 7 | `cloudbaserc.json` 只声明 2 个函数 | 声明式全量部署会漏 5 个 | 补齐 7 个函数配置 |
| 8 | 依赖 peer 冲突 | Taro 4.1.9 要求 `webpack@5.91.0`，锁定 5.78.0 | 安装需 `--legacy-peer-deps`，建议后续对齐版本 |
